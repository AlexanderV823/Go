# REST API для блога на Go (Blog-API)

Промышленное REST API для блога с поддержкой JWT-авторизации, публикаций, комментариев, структурированного логирования, автоматических транзакционных миграций и многопоточного Rate Limiter. Проект спроектирован по принципам Чистой Архитектуры (Clean Architecture) с полной инверсией зависимостей через Go-интерфейсы.

## 🚀 Основные возможности

- **Аутентификация и Безопасность**:
  - Регистрация и вход с валидацией email стандартными средствами RFC (`net/mail`).
  - Генерация криптографически подписанных JWT-токенов (HS256).
  - Защита от race condition при конкурентной регистрации уникальных сущностей (`unique_violation` PostgreSQL перехватывается и мапится в `409 Conflict`).
- **Управление публикациями и комментариями**:
  - Создание, чтение, строго валидированная пагинация, обновление и удаление.
  - Контроль прав доступа: изменять и удалять ресурсы может только их непосредственный автор (`403 Forbidden`).
  - Предварительная валидация внешних ключей в слое бизнес-логики: создание комментария к несуществующему посту перехватывается до обращения к БД и возвращает `404 Not Found`.
- **Строгая валидация и защита памяти (Хартнинг Handler-слоя)**:
  - Ограничение размера входящего тела запроса через `http.MaxBytesReader` (защита от OOM и DoS атак).
  - Запрет неконтрактных и избыточных данных через `DisallowUnknownFields`.
  - Валидация JSON-потока на отсутствие лишних байт и вторых объектов после завершения валидной структуры.
  - Измерение длины строк исключительно в **рунах (UTF-8)** через `utf8.RuneCountInString`, что гарантирует корректный учет кириллицы, в отличие от байтового `len()`. Очистка внешних пробелов через `strings.TrimSpace`.
- **Инфраструктурные Middleware**:
  - `Recovery` — автоматический перехват паник для предотвращения падения сервера.
  - `RequestID` — генерация сквозного ID для трассировки цепочки логов.
  - `CORS` — гибкая настройка заголовков для работы с фронтендом.
  - `RateLimiter` — потокобезопасный Token Bucket с поддержкой `float64`-точности накопления, защитой от утечек памяти (автоочистка неактивных IP по TTL) и устойчивостью к спуфингу заголовков (используется физический `r.RemoteAddr`).
  - `Logger` — детальные логи запросов с подсчетом байт ответа и времени обработки.
- **База данных и Health Check**:
  - Автоматические транзакционные миграции схемы данных при старте сервиса из кода.
  - Осмысленный (meaningful) `/api/health` эндпоинт: выполняет `PingContext` и тестовый легковесный `SELECT` к таблицам схемы с коротким тайм-аутом. Возвращает `503 Service Unavailable` при сбое СУБД или отсутствии таблиц.

## 🛠 Технологический стек

- **Язык**: Go (Golang) 1.20+
- **HTTP Роутер**: [go-chi/v5](https://github.com/go-chi/chi/v5)
- **База данных**: PostgreSQL
- **Драйвер БД**: [lib/pq](https://github.com/lib/pq)
- **Конфигурация**: Environment Variables через [godotenv](https://github.com/joho/godotenv)
- **Контейнеризация**: Docker & Docker Compose

## 💻 Быстрый старт

### 1. Подготовка конфигурации
Перед запуском создайте файл `.env` в корневой папке проекта:

```env
# Настройки сервера Go
SERVER_PORT=8080
SERVER_HOST=0.0.0.0

# Настройки PostgreSQL для Docker и Go
DB_HOST=127.0.0.1
DB_PORT=5432
DB_USER=bloguser
DB_PASSWORD=blogpassword
DB_NAME=blogdb
DB_SSL_MODE=disable

# Безопасность (JWT)
JWT_SECRET=super-secure-random-secret-key-32-chars
JWT_EXPIRY_HOURS=24
```

### 2. Запуск приложения

#### Вариант А. Автоматизированный запуск через `Makefile`
```bash
make dev
```
*Для плавной остановки сервера и очистки контейнеров нажмите `Ctrl+C` в терминале.*

#### Вариант Б. Ручной запуск
1. Поднимите контейнер базы данных:
   ```bash
   docker-compose up -d postgres
   ```
2. Установите зависимости и запустите API-сервер:
   ```bash
   go mod tidy
   ```
3. Запустите API-сервер:
   ```bash
   go run cmd/api/main.go
   ```

При успешном запуске в консоли появятся логи:
```text
Successfully connected to the database
Running database migrations...
Database migrations applied successfully
Starting HTTP server on 0.0.0.0:8080
```

## 🧪 Тестирование

### 1. Модульное тестирование (Unit Tests)
Благодаря переходу слоев `Service` на интерфейсы репозиториев (`interfaces.go`), бизнес-логика полностью изолирована. Проект покрыт unit-тестами с использованием легковесных тест-стабов без сторонних mock-генераторов. Тесты проверяют валидацию кириллицы, обработку race-condition и реакцию на несуществующие ID.

Запуск модульных тестов:
```bash
go test -v -race ./internal/service/...
```

### 2. Сквозное автоматизированное тестирование (E2E Integration Тесты)
В корне находится строгий тестовый сценарий `test_api.sh`. Он валидирует HTTP статус-коды, структуру JSON и бизнес-ограничения, падая при малейшем нарушении контракта.

Скрипт проверяет:
- **Happy Path**: Регистрация, авторизация, извлечение токена, создание поста, валидация лимитов пагинации, комментирование, обновление и каскадное удаление.
- **Negative & Security Path**: Блокировка запросов без токена (`401`), блокировка запросов с поврежденным JWT (`401`), попытка изменения чужих постов (`403 Forbidden`), комментирование несуществующих постов (`404`), передача невалидных query-параметров (`400 Bad Request`).

Запуск интеграционного теста:
```bash
./test_api.sh
```

## 🎯 Спецификация API и Правила Валидации

### Формат Ошибок
Все ошибки во всех обработчиках унифицированы и возвращаются строго в формате JSON с MIME-типом `application/json; charset=utf-8`:
```json
{
  "error": "Описание ошибки для клиента"
}
```

### Основные эндпоинты

| Метод      | Эндпоинт                   | Права         | Ограничения и Валидация                                                                                          |
| :--------- | :------------------------- | :------------ | :--------------------------------------------------------------------------------------------------------------- |
| **POST**   | `/api/register`            | Публичный     | Тело до 1 МБ. `username` (3-50 рун), `email` (RFC валидация), `password` (мин. 6 рун). Возвращает `201 Created`. |
| **POST**   | `/api/login`               | Публичный     | Тело до 1 МБ. Строгая проверка валидности. Возвращает `200 OK` + JWT.                                            |
| **GET**    | `/api/posts`               | Публичный     | Query: `limit` (число >0 до 100, по деф. 10), `offset` (число >=0). При ошибке формата — `400 Bad Request`.      |
| **GET**    | `/api/posts/{id}`          | Публичный     | Поиск публикации по ID. При отсутствии — `404 Not Found`.                                                        |
| **POST**   | `/api/posts`               | **JWT**       | Тело до 2 МБ. `title` (5-200 рун), `content` (10-50000 рун). Возвращает `201 Created`.                           |
| **PUT**    | `/api/posts/{id}`          | **JWT Автор** | Обновление полей. Только для автора поста, иначе `403 Forbidden`.                                                |
| **DELETE** | `/api/posts/{id}`          | **JWT Автор** | Удаление публикации. Только для автора поста, иначе `403 Forbidden`. Возвращает `204 No Content`.                |
| **POST**   | `/api/posts/{id}/comments` | **JWT**       | Тело до 256 КБ. `content` (1-2000 рун). Контроль существования поста (`404`). Возвращает `201 Created`.          |
| **PUT**    | `/api/comments/{id}`       | **JWT Автор** | Редактирование текста комментария (1-2000 рун). Только для автора, иначе `403`.                                  |
| **DELETE** | `/api/comments/{id}`       | **JWT Автор** | Удаление комментария. Только для автора, иначе `403`. Возвращает `204 No Content`.                               |
| **GET**    | `/api/health`              | Публичный     | Тайм-аут проверки СУБД 2 сек. При аварии БД или отсутствии таблиц — `503`.                                       |
